# PRD v3 — карточки для повторения из конспекта

**Версия:** 3.0 · 16.10.2026  
**Скоуп:** `docs/mvp-scope.md` · **UC:** `docs/use-cases/README.md` · **дельта:** `docs/use-cases/requirements-v3.md`

## Проблема

Студенту трудно превратить длинный PDF-конспект в короткий набор вопросов для устной защиты и объективно проверить ответ, сформулированный своими словами.

## Боли пользователя (проверяются приёмкой Lab 5)

1. Долго превращать PDF в вопросы вручную.
2. Нельзя проверить ответ, сформулированный своими словами.
3. Неясно, откуда взят правильный ответ.
4. Прогресс подготовки теряется между заходами.
5. Ошибка загруженного файла непонятна: неясно, что исправить.

## Пользователь и основной сценарий

Студент загружает один PDF, получает 5–10 grounded-карточек, отвечает в Telegram или web, видит объяснимую оценку, отмечает полезность карточки и продолжает с сохранённого места. Система соблюдает суточный бюджет и не даёт модели выполнять необратимые действия.

## Требования v3

1. Карточка содержит страницу и дословную цитату из загруженного PDF.
2. Проверка принимает смысловой эквивалент, но не противоречие источнику; эталон только из БД.
3. Ошибка модели, лимит или таймаут — понятное сообщение; сессия не повреждается.
4. Необратимые операции и доступ к данным разрешает приложение, а не LLM (UC-03, UC-07).
5. ≤50 модельных запросов и ≤120 000 оценочных токенов на пользователя в сутки; после 80% — дешёвая модель; при 100% — отказ (UC-06).
6. Повтор владельца с тем же idempotency key, содержимым, операцией и версией промпта не списывает бюджет и не создаёт дубликат; конфликт содержимого даёт 409, запрос без identity не раскрывает сохранённый результат.
7. Каждый релиз: unit/integration/security tests и полный golden eval.
8. Основной вход — PDF с текстовым слоем; базовый OCR читаемых печатных сканов допустим; рукопись вне MVP.

## North Star и защитные метрики

- **North Star:** ≥**70%** начатых учебных сессий завершаются минимум по **пяти** карточкам.

### Способ замера North Star (записан в PRD)

- Источник: серверные записи `study_sessions` (поле `current_position`); Telegram/Web пишут прогресс только через backend (`POST /v1/ai/sessions`, `PATCH /sessions/{id}/progress`).
- Формула: `completed_5_rate = sessions(current_position >= 5) / sessions(started in period)`.
- Когорта: только внешние пользователи; командные и smoke/CI-аккаунты исключаются.
- Период фиксируется в UTC; флаг `completed` не используется, критерий — именно `current_position >= 5`.
- Расчёт воспроизводится скриптом `scripts/measure_north_star.py` по экспорту сессий; результат — `artifacts/product/north-star-measurement.json`.
- Подтверждение цели для Demo Day: минимум 10 внешних сессий, из них ≥7 достигли пяти карточек.
- ≥85% внешних пользователей завершают UC-01…UC-05 без подсказки команды.
- Доля оценок «Полезно» — вспомогательная UX-метрика (не заменяет North Star).
- Schema validity и grounding — 100% на golden dataset.
- Review agreement — ≥85% (точка отсчёта Lab 3: 90,48% deterministic fallback).
- p95 API без провайдера — ≤500 мс; p95 модельного вызова — отдельно.
- Непонятные ошибки — &lt;2% запросов.
- Бюджетная аномалия создаёт алерт до полного выгорания лимита.

## Ограничения и риски

- `X-User-ID` — доверенный клиентский идентификатор прототипа, а не полноценная аутентификация; перед публичным запуском требуется проверенный Telegram login/session token.

Цифры deterministic fallback нельзя выдавать за качество или latency Gemini. Для публичной продажи нужны управляемая production-БД, бэкапы, Redis limiter при масштабировании и юридическая проверка документов.
