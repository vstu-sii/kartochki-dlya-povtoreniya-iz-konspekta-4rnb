# Доказательства AI-критериев из Lab 1

**Статус:** подготовлен воспроизводимый пакет; ручные оценки, исходные PDF и live-замеры ожидают совместного прогона AI + Quality + Delivery.

Этот документ не подменяет отсутствующие измерения нулями. Исходные строки и поля для разметки лежат в `artifacts/evals/lab1-ai-quality-evidence.json`.

## Что уже подготовлено

- Ровно 20 разборов ответов из версионированного golden dataset.
- Для каждой строки сохранены вопрос, ответ студента, эталон, исходный контекст, обязательные пункты и полный результат системы.
- Сохранены модель, версия промпта, latency и usage каждого разбора.
- На подготовленных 20 строках автоматическое совпадение verdict с эталоном — 20/20 (100%); это только техническая метрика, не итог ручной приёмки.
- Для совместного ревью есть четыре независимых поля: отсутствие противоречий, полнота обязательных пунктов, критическое и мелкое нарушение тона.
- Записаны формулы подсчёта, цели Lab 1 и незакрытые входные данные.

## 1. Тезисы из PDF — требуется ручной проход

В репозитории сейчас нет исходных PDF, поэтому процент не рассчитан. Для каждого PDF AI Engineer и Quality вместе:

1. выписывают проверяемые тезисы из исходного PDF;
2. рядом фиксируют тезис/карточку системы;
3. отмечают `correct=true/false` и короткую причину;
4. считают `верные / проверенные`.

Цель: не менее 75%. В JSON нужно заполнить `pdf_thesis_check.documents`, затем итоговые `checked_theses`, `correct_theses` и `accuracy`.

## 2. Двадцать разборов ответов — готово к совместной разметке

Quality заполняет в каждой строке `quality_manual_review` только булевы поля и имя проверяющего. Правила:

- `no_contradiction=true`, если verdict и feedback не утверждают ничего, что противоречит эталону и исходному контексту;
- `mandatory_points_complete=true`, если результат системы корректно учитывает обязательные пункты ответа и не теряет значимые пропуски;
- `critical_tone_violation=true` для оскорбления, угрозы, дискриминации или другого недопустимого обращения;
- `minor_tone_violation=true` для некритичной, но неуместной формулировки. Одна строка считается один раз.

После разметки считаются четыре отдельные метрики:

| Метрика | Формула | Цель |
|---|---|---:|
| Нет противоречий | `no_contradiction=true / 20` | ≥90% |
| Полнота обязательных пунктов | `mandatory_points_complete=true / 20` | ≥80% |
| Критические нарушения тона | количество `true` | 0 |
| Мелкие нарушения тона | количество `true / 20` | ≤5% |

Автоматическое совпадение verdict с golden dataset — дополнительная техническая метрика, но оно не заменяет эти четыре ручные оценки.

После заполнения сырых полей итог вычисляется без перегенерации строк и без стирания разметки:

```powershell
py -3 -m tests.evals.prepare_lab1_quality_evidence --summarize-existing
```

## 3. Формулы в PDF — требуется исходный корпус

Для каждого PDF вручную считается число самостоятельных формул в оригинале и после извлечения текста. Потеря:

`(формулы в PDF − формулы после извлечения) / формулы в PDF`.

Цель: строго меньше 10%. Если в выбранном PDF формул нет, он не подходит как единственный пример: деление на ноль не является доказательством.

## 4. Фактическая стоимость полного сценария — требуется live-прогон

Нужен один и тот же реальный сценарий: загрузка PDF, генерация карточек и разборы ответов. Из ответов/трасс записываются фактические input/output tokens и фактически использованная модель, включая fallback.

Формула:

`input_tokens / 1 000 000 × input_price + output_tokens / 1 000 000 × output_price`.

План Lab 1: около 18 500 токенов на сессию и 0 рублей только в пределах Free tier. Ноль в Free tier не означает отсутствие потребления: в отчёте всё равно показываются токены и расчёт по стандартному тарифу. Имеющийся usage двадцати разборов сохранён как частичный замер и не называется стоимостью полного сценария.

## 5. Время вместе с Delivery — требуется работающее приложение

На одной версии, окружении и модели выполняются несколько отдельных запусков. Для каждого сохраняется сырой результат:

- от отправки PDF до получения готового набора, цель p95 < 60 000 мс;
- от отправки ответа до получения разбора, цель p95 ≤ 7 000 мс (целевой диапазон 5–7 секунд).

В отчёте обязательны число запусков, все отдельные значения, p95, дата, окружение, SHA/тег и модель. Локальные миллисекунды deterministic-runner подтверждают только скорость алгоритма и не засчитываются как end-to-end замер.
