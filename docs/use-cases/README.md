# Use cases MVP

Use cases описывают MVP глазами студента технического вуза, который готовится к устной защите одной лабораторной.

**Актуализация лабораторной 3:** изменения после прогона прототипа зафиксированы в `requirements-v2.md`. Валидация на живом прототипе: `validation-lab3.md`. Итоги спринта: `../iteration-notes.md`. Проживаемость макета Lab 2: `validation.md`. Диаграмма: `use-cases.puml`.

## UC-01 — Создать карточки из PDF

**Актёр:** студент.  
**Цель:** за одну минуту получить вопросы по своей методичке.  
**Контекст:** до защиты один-два дня; у студента есть PDF до **10 МБ**, не более 40 страниц и 60 000 оценочных токенов. Документ может иметь текстовый слой или быть читаемым сканом (OCR).  
**Предусловия:** бот доступен; пользователь открыл новую сессию; лимит запросов не исчерпан.

**Основной сценарий:**

1. Студент нажимает «Новая подготовка».
2. Бот просит загрузить одну PDF-методичку и показывает ограничения.
3. Студент отправляет PDF.
4. Система проверяет MIME и размер; извлекает текстовый слой; для страниц без текста применяет OCR.
5. Система нормализует текст с номерами страниц и генерирует карточки (целевой диапазон 5–10; при нехватке независимых тезисов — меньше пяти без дублей).
6. Система проверяет структуру, уникальность и цитату-основание каждой карточки.
7. Бот показывает название набора, число карточек и кнопку «Начать повторение».

**Результат:** создан набор карточек; каждая содержит вопрос, эталон, страницу и подтверждённую цитату.  
**Как поймём, что работает:** 100% карточек проходят JSON Schema и grounding check; набор готов ≤60 секунд; ≥80% вопросов пользователь оценивает как полезные.

**Альтернативы и исключения:**

- не PDF или файл >10 МБ — бот объясняет ограничение и не вызывает модель;
- неразборчивый, зашифрованный или полностью пустой после OCR PDF — стабильный код ошибки до вызова модели;
- рукопись и OCR «как отдельный продукт» не входят в MVP (см. не-скоуп roadmap);
- >40 страниц или >60 000 токенов — бот просит загрузить только раздел по текущей лабораторной;
- материала недостаточно для пяти независимых тезисов — набор может содержать **меньше пяти** карточек; UI объясняет причину;
- primary недоступна — один вызов fallback; при общем сбое провайдера возвращается повторяемая ошибка без дублирования набора.

## UC-02 — Пройти раунд вопрос–ответ

**Актёр:** студент.  
**Цель:** проверить, может ли он сформулировать ответ своими словами.  
**Контекст:** набор карточек уже создан.  
**Предусловия:** в наборе есть хотя бы одна непройденная карточка.

**Основной сценарий:**

1. Студент нажимает «Начать повторение».
2. Бот показывает один вопрос без эталона.
3. Студент вводит текстовый ответ до 2 000 символов.
4. Система передаёт модели только вопрос, эталон, цитату и текущий ответ.
5. Бот показывает вердикт: «верно», «частично» или «неверно», короткую обратную связь и пропущенные пункты.
6. Студент нажимает «Следующий вопрос».

**Результат:** ответ сохранён в сессии, прогресс увеличен на одну карточку.  
**Как поймём, что работает:** ответ приходит ≤7 секунд по p95; вердикт не противоречит эталону; модель не использует сведения вне цитаты/эталона.

**Альтернативы и исключения:**

- пустой ответ — бот просит ввести ответ;
- ответ >2 000 символов — бот просит сократить;
- короткий ответ нельзя считать неверным только из-за малого лексического пересечения; `incorrect` требует подтверждённого противоречия или отсутствия ключевого тезиса;
- feedback показывает, какой пункт эталона отсутствует, но не раскрывает весь эталон до завершения попытки;
- модель недоступна — ответ не теряется, предлагается повторить запрос с тем же idempotency key;
- студент нажимает «Не знаю» / «Пропустить» — показывается эталон, результат отмечается как `skipped` без вызова модели.

## UC-03 — Оценить полезность карточки

**Актёр:** студент.  
**Цель:** сообщить, помогает ли конкретный вопрос готовиться.  
**Контекст:** студент увидел вопрос или завершил его разбор.  
**Предусловия:** карточка принадлежит текущей сессии.

**Основной сценарий:**

1. Бот предлагает кнопки «Полезно» и «Не полезно» (допустимы формулировки «Не по теме»).
2. Студент выбирает одну оценку.
3. Система атомарно сохраняет актуальную оценку пары session/card и отдельно пишет событие в `card_rating_events`.
4. Бот подтверждает оценку и продолжает сессию.

**Результат:** актуальная оценка учтена в метрике полезности; история изменений доступна для аудита.  
**Как поймём, что работает:** одна актуальная оценка на карточку; при смене оценки в БД — новое значение и как минимум два события истории; агрегат строится без текста PDF и личности студента.

**Альтернативы и исключения:** повторная оценка заменяет предыдущую; агрегированный отчёт истории для команды — расширение после MVP; недоступность БД не блокирует просмотр следующего вопроса, но событие ставится на повторную запись.

## UC-04 — Завершить и возобновить сессию

**Актёр:** студент.  
**Цель:** увидеть итог и продолжить незаконченный набор позже.  
**Контекст:** пройдена хотя бы одна карточка.  
**Предусловия:** сессия существует и принадлежит этому Telegram-пользователю (или Web session id).

**Основной сценарий:**

1. Студент нажимает «Завершить» или отвечает на последнюю карточку.
2. Бот показывает количество `correct`, `partially_correct`, `incorrect`, `skipped`.
3. При незавершённой сессии бот сохраняет позицию в БД.
4. При следующем входе (`/start` или «Продолжить») студент возвращается к первой непройденной карточке.
5. После перезапуска Web/Telegram-адаптера позиция восстанавливается из БД.

**Результат:** прогресс не теряется; студент понимает слабые темы.  
**Как поймём, что работает:** позиция и агрегаты совпадают с событиями ответов; пользователь не видит чужие сессии.

**Альтернативы и исключения:** сессия старше 30 дней отклоняется стабильной ошибкой; физическая фоновая очистка записей — задача спринта 4; после удаления пользовательских данных возобновление невозможно.

## UC-05 — Безопасно отклонить неподдерживаемый документ

**Актёр:** студент.  
**Цель:** получить понятное действие вместо зависания или плохих карточек.  
**Контекст:** загружен не-PDF, повреждённый, слишком большой, зашифрованный или нечитаемый после OCR документ, либо PDF с вредоносными инструкциями.  
**Предусловия:** файл дошёл до backend.

**Основной сценарий:**

1. Система валидирует MIME, размер и извлекаемый/OCR-текст до обращения к модели.
2. Система считает извлечённый текст недоверенными данными и не исполняет инструкции из него.
3. При нарушении технического ограничения система возвращает стабильный код ошибки.
4. Бот переводит код в понятное сообщение и подсказывает исправление.

**Результат:** модель не получает недопустимый документ; пользователь понимает следующий шаг.  
**Как поймём, что работает:** 100% тестовых неподдерживаемых файлов завершаются управляемой ошибкой; секреты и системный промпт не попадают в ответ или логи.

**Альтернативы и исключения:** prompt injection в обычном текстовом PDF не блокирует весь документ и не исполняется; модель не имеет инструментов; каждая карточка проходит grounding check и обязана иметь дословную цитату из страницы.
