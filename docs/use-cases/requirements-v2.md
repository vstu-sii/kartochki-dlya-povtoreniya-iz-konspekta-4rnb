# Требования v2 после встречи с прототипом

Изменения относительно прежней версии use cases отмечены явно. Актуальный канон сценариев — `README.md` в этой папке; этот файл фиксирует **дельты** после валидации прототипа Lab 3.

## Изменено

- **UC-01:** Telegram принимает один PDF до **10 МБ** (было 20 МБ). API сначала читает текстовый слой; для сканированных страниц применяет **OCR**. Неразборчивый, зашифрованный или превышающий лимиты PDF получает стабильный код ошибки до вызова модели. Рукопись и «OCR как отдельный продукт» остаются вне MVP.
- **UC-01:** при недостатке независимых тезисов набор может содержать **меньше пяти** карточек вместо повторения одной формулировки. UI объясняет причину.
- **UC-02:** короткий ответ нельзя считать неверным только из-за малого лексического пересечения; verdict `incorrect` требует подтверждённого противоречия или отсутствия ключевого тезиса.
- **UC-02:** feedback обязательно показывает, какой пункт эталона отсутствует, но не раскрывает весь эталон до завершения попытки.
- **UC-03:** повторная оценка атомарно заменяет текущее значение пары session/card; каждое изменение отдельно сохраняется в `card_rating_events`. Агрегированный отчёт истории для команды остаётся расширением после MVP.
- **UC-04:** resume открывает первую непройденную карточку после `/start` и после перезапуска Web/Telegram. Сессия старше 30 дней считается просроченной и не открывается; физическая фоновая очистка записей — задача спринта 4.
- **UC-05:** не-PDF (например PNG) и нечитаемые документы отклоняются до модели; prompt injection в материале не исполняется; карточка всё равно обязана иметь дословную цитату из страницы.

## Не изменено

Лимиты 40 страниц / 60 000 оценочных токенов, целевой запрос 5–10 карточек, p95 генерации 60 секунд, p95 review 7 секунд и запрет на чужие сведения остаются критериями целевого MVP.

## Статус реализации на 15.10.2026

OCR для читаемых сканов, история рейтингов и проверка срока сессии реализованы Delivery и подтверждены автоматическими проверками (`../quality/verification-2026-10-15.md`) и ручным прогоном внешнего студента Постернака Дениса (`validation-lab3.md`).

Проверка владельца по `X-User-ID` пока не является серверной аутентификацией; полноценная защита чужих данных остаётся открытой задачей Delivery (спринт 4, P1).
