# Roadmap и скоуп MVP

## Цель Demo Day

Студент отправляет PDF одной лабораторной в Telegram, получает 5–10 подтверждённых источником вопросов, отвечает текстом, получает обратную связь и видит итог сессии. Команда демонстрирует измеренные качество, задержку и стоимость на golden dataset.

## MVP-скоуп

| Возможность | UC | Критерий готовности |
|---|---|---|
| PDF с текстовым слоем | UC-01, UC-05 | ограничения проверяются до LLM, ошибки понятны |
| 5–10 карточек | UC-01 | JSON Schema + подтверждённая цитата каждой карточки |
| Текстовый ответ | UC-02 | один вопрос за раз, вердикт и пропущенные пункты |
| Оценка полезности | UC-03 | одна актуальная оценка на карточку |
| Прогресс сессии | UC-04 | завершение, итог, продолжение |
| Primary/fallback модель | UC-01, UC-02 | модель и факт fallback видны в telemetry |
| Evals и безопасность | все | golden dataset, регрессия, prompt-injection тесты |

## Явный не-скоуп

| Возможность вне MVP | Почему осознанно исключена |
|---|---|
| OCR рукописных конспектов и сканов без текстового слоя | Качество OCR зависит от почерка и языка и требует отдельного датасета; для Demo Day принимаются только PDF с извлекаемым текстом. |
| DOCX, изображения, аудио и ссылки на сайты | Каждый формат требует отдельного безопасного parser/loader и расширяет поверхность атак; MVP проверяет один контролируемый вход — PDF. |
| Голосовой ввод/вывод и STT/TTS | Не относится к проверяемой гипотезе генерации и устной тренировки по содержанию; добавляет разрешения, стоимость и обработку аудиоданных. |
| Подготовка ко всему экзамену или работа с несколькими документами | Усложняет ownership, дедупликацию, контекст и навигацию; MVP ограничен одной лабораторной и одной активной сессией. |
| RAG, векторная БД, интернет-поиск и многошаговый агент | Для одного ограниченного PDF прямой промпт дешевле и проще; выигрыш RAG ещё не подтверждён экспериментом, а интернет ухудшает grounding к источнику пользователя. |
| Автоматическое редактирование учебных материалов | Модель не должна изменять источник пользователя; продукт только создаёт карточки и обратную связь. |
| Кабинет преподавателя, совместные наборы и публичный каталог | Требуют ролей, модерации, совместного доступа и отдельной модели персональных данных; это не нужно для индивидуального happy path. |
| Мобильное приложение вне Telegram | Telegram уже предоставляет авторизацию, доставку сообщений и доступ с телефона; отдельное приложение не проверяет новую продуктовую гипотезу. |
| Гарантированная педагогическая или фактическая безошибочность | Абсолютную гарантию для генеративной модели доказать нельзя; MVP вместо неё измеряет grounding, полезность и показывает цитату-основание. |

## Вехи

| Веха | Результат | Выходной критерий |
|---|---|---|
| Лаба 2 — чертежи | UC, C4, ADR, ERD, OpenAPI, DoD, 120 eval-кейсов, threat model, прототип | локальные проверки зелёные; ручные пункты явно отмечены |
| Лаба 3 — MVP | Telegram-бот, PDF parser, AI gateway, БД, CI mini-evals | happy path UC-01/02 работает end-to-end |
| Лаба 4 — production-ready | секреты, лимиты, мониторинг, бэкапы, атаки | threat cases проходят; compose/production health checks зелёные |
| Лаба 5 — метрики | полный eval, latency/cost dashboard, исправления | полезность ≥80%, grounding ≥95%, p95 ответа ≤7 с |
| Лаба 6 — Demo Day | воспроизводимая демонстрация и отчёт | новый PDF → итог сессии без ручных обходов |

## Правила изменения скоупа

Новая функция попадает в MVP только если привязана к боли из `docs/prd.md`, имеет UC и измеримый критерий, а команда явно снимает задачу сопоставимого размера. RAG добавляется только при выполнении условий из `docs/ai-pipeline.md`.
