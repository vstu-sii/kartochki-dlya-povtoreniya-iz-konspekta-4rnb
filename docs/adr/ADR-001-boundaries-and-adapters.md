# ADR-001: Границы ядра и внешних адаптеров

## Контекст

Продукт зависит от Telegram и облачной LLM, чьи API, ошибки и форматы меняются независимо от предметной логики карточек. Команда из четырёх человек должна разрабатывать части параллельно и иметь возможность заменить провайдера.

## Решение

Выделяем отдельно запускаемые контейнеры: Telegram Adapter, Application API, AI Service и Data Service. Telegram Adapter и AI Service являются anti-corruption layers: только они знают внешние API. Application API оркестрирует use cases в терминах доменных схем. Data Service — единственный владелец PostgreSQL.

Схема: `docs/architecture/c4-container.puml`.

## Обоснование

Альтернатива — один бот, напрямую работающий с БД и Gemini. Она быстрее в первые часы, но связывает Telegram handlers, модельные DTO и хранение, мешая Delivery и AI Engineer работать параллельно. Выбранные границы совпадают с независимыми причинами изменения.

## Цена решения

Четыре процесса вместо одного: больше Dockerfile, health checks, сетевых вызовов и логов. Для маленькой команды это операционная нагрузка; интерфейсы между контейнерами придётся версионировать. Мы принимаем её ради изоляции внешних API и явного владельца данных.

### Лимиты MVP

- не более **4 отдельно запускаемых прикладных контейнеров** до Demo Day; новый контейнер требует отдельного ADR;
- не более **4 внутренних HTTP-вызовов** на happy path генерации карточек без учёта вызова Gemini;
- суммарный p95 накладных расходов внутренних HTTP-вызовов — не более **500 мс** на локальном стенде без времени LLM;
- все четыре контейнера должны перейти в состояние healthy не позднее **120 секунд** после `docker compose up --build --wait`;
- изменение межсервисного контракта выполняется только новой версией OpenAPI/схемы и contract test, без неявной совместимости.

### Условия пересмотра

Решение пересматривается отдельным ADR, если хотя бы один порог нарушен в двух последовательных измерениях, запуск Compose превышает 120 секунд, для одного use case требуется пятый контейнер или поддержка контрактов занимает более **20% задач спринта**. В этом случае команда сравнивает текущую схему с объединением Application API и Data Service либо с выносом конкретного узкого сервиса.

## Как покрыть тестами

- `aact check`: отсутствие прямых связей Application API → Telegram/Gemini и нескольких владельцев БД;
- contract tests для OpenAPI AI Service;
- интеграционный тест Telegram Adapter → Application API с mock;
- архитектурный тест проверяет разрешённые связи из C4.
